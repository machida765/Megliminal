# テスト方針

手動で触って確認する項目は [`テスト計画/テスト計画書.md`](./テスト計画/テスト計画書.md)（チェックリスト形式）。  
この文書は自動テストの層分けとコマンドをまとめたものです。

## 3 層の使い分け

| 層 | ツール | 置き場所 | 対象 | Supabase |
|---|---|---|---|---|
| 単体 | Vitest | `tests/unit/` | Zod スキーマ、ランキング集計、投稿頻度、認可ヘルパー | 不要 |
| 結合 | Vitest | `tests/integration/` | RLS ポリシーと DB トリガー | ローカル起動が必要 |
| E2E | Playwright | `tests/e2e/` | 認証フローと投稿 CRUD をブラウザで通す | ローカル起動 + dev サーバー |

単体テストは純粋関数だけを見る。DB の振る舞い（誰が何を書けるか、like_count が増えるか、
退会で CASCADE するか）は結合テストで実物に当てる。画面の導線は E2E で確認する。

## コマンド

```bash
npm test                  # 単体テスト
npm run test:watch        # 単体テストを watch
npm run test:coverage     # 単体テスト + カバレッジ
npm run test:integration  # RLS 結合テスト（要 supabase start）
npm run test:e2e          # E2E（dev サーバーは Playwright が起動する）
npm run test:e2e:install  # Playwright のブラウザ取得（初回のみ）
```

## 前提と環境変数

結合テストと E2E は `.env.local` を読む（`tests/load-env.ts`）。以下が必要。

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- `SUPABASE_SERVICE_ROLE_KEY`

値は `npm run supabase:status` の `API_URL` / `PUBLISHABLE_KEY` / `SECRET_KEY` から取る。
`SUPABASE_SERVICE_ROLE_KEY` はテストユーザーの作成と削除にだけ使う。

ローカル Supabase が起きていない場合、結合テストは失敗ではなくスキップされる。

## 注意点

- **テストユーザーは毎回作り捨て**。`tests/e2e/fixtures.ts` と
  `tests/integration/setup.ts` が Auth Admin API でユーザーを作り、終了時に削除する。
  投稿やコメントは CASCADE で一緒に消えるので後片付けは不要。
- **週1投稿制限**があるため、投稿系のテストは毎回新しいユーザーで動かす。
  既存ユーザーを使い回すと 2 本目の投稿が弾かれる。
- **E2E は dev サーバーで動かす**。本番 CSP は http のローカル Supabase を
  `connect-src` に許可しないため、`next start` では通信がブロックされる。
- **既に dev サーバーが動いているとき**は `E2E_BASE_URL` を渡すとそれを使う。

  ```powershell
  $env:E2E_BASE_URL="http://localhost:3000"; npx playwright test
  ```

- Node.js 22 未満では `@supabase/supabase-js` が要求するグローバル `WebSocket` が無いため、
  `tests/polyfill-websocket.ts` が undici で補っている。Node 22 以降なら何もしない。

## CI

`.github/workflows/ci.yml` が 3 ジョブを並列で回す。

1. `static` — lint / 型チェック / 単体テスト + カバレッジ
2. `audit` — 本番依存の脆弱性チェック
3. `supabase` — Supabase CLI を起動して RLS 結合テストと E2E

`supabase status -o env` で取った接続情報を `GITHUB_ENV` に流し込むため、
CI 側にシークレットを登録する必要はない（ローカル Supabase の固定キーを使う）。
