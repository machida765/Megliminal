## シナリオ A: 未ログインで `/create` にアクセス

### 流れ

```
GET /create
  → middleware.ts (updateSession)
  → user === null && isLoginRequired
  → redirect /login?redirect=/create
```

### 該当コード

```44:51:lib/supabase/middleware.ts
  const loginRequiredPaths = ['/create', '/profile/edit', '/settings', '/bookmarks', '/reset-password'];
  const isLoginRequired = loginRequiredPaths.some((p) => pathname.startsWith(p));
  const isEditPost = /^\/post\/[^/]+\/edit/.test(pathname);
  const isAdminPath = pathname.startsWith('/admin');

  if (!user && (isLoginRequired || isEditPost || isAdminPath)) {
    return redirectToLogin(request, pathname);
  }
```

### 学び

- middleware は **ページ表示の前** に動く（Server Component より前）
- `getUser()` で JWT を検証し、Cookie を refresh する
- ここは **認可の第1層**（ページ単位）。DB 操作はまだ起きていない

### ログイン後の redirect

```5:20:lib/auth/safe-redirect.ts
export function getSafeRedirectPath(
  value: string | null | undefined,
  fallback = '/'
): string {
  if (
    !value ||
    !value.startsWith('/') ||
    value.startsWith('//') ||
    value.includes('\\') ||
    /[\u0000-\u001f\u007f]/.test(value)
  ) {
    return fallback;
  }

  return value;
}
```

`/login?redirect=//evil.com` → fallback `/` に落ちる。**Open Redirect 防止**。

## シナリオ B: 投稿を作成する

### 流れ（正常系）


### assertActingAs — なりすまし防止


## シナリオ C: 他人の投稿を削除しようとする

### 攻撃者の操作

```javascript
// コンソールから（仮）
repository.deletePost('他人の-post-uuid')
```

### 防御の順番

```
1. assertCanChangePosts(['他人の-post-uuid'])
   → DB から posts.user_id を SELECT
   → authenticatedUserId !== post.user_id
   → allowAdmin=false なので throw

2. (万が一 assert を bypass した場合)
   RLS posts_delete_own: auth.uid() = user_id → DELETE 0 rows
```

### assertCanChangePosts の核心

```108:114:lib/data/supabase-repository.ts
  private async assertCanChangePosts(
    ids: string[],
    allowAdmin = false

    const validatedIds = ids.map((id) => postIdSchema.parse(id));
    const uniqueIds = [...new Set(validatedIds)];
    const authenticatedUserId = await this.getAuthenticatedUserId();
```

**重要:** 所有者判定に **クライアントが送った userId を使わない**。DB から `user_id` を読む。

### admin 一括削除

```468:474:lib/data/supabase-repository.ts
    const validatedIds = await this.assertCanChangePosts(ids, true);

    const { error } = await this.client
      .from('posts')
      .delete()

```

`allowAdmin: true` のときだけ `profiles.role === 'admin'` を許可。RLS 側も `posts_delete_admin` ポリシーがある。

## シナリオ D: 退会 API

Megliminal で **唯一のカスタム状態変更 API**。

### 流れ

```
POST /api/account/delete { password: "..." }
  → createClient().auth.getUser()     セッション確認
  → deleteAccountSchema.safeParse     Zod
  → signInWithPassword                本人確認（メールユーザー）
  → createAdminClient()               service_role
  → auth.admin.deleteUser(user.id)    Auth ユーザー削除
  → CASCADE で profiles, posts 等も削除

  → { success: true }
```

### なぜ service_role？

`auth.users` の削除は Admin API のみ。anon key + RLS では消せない。

### CSRF の論点

この API は **Cookie セッション** で認証される。悪意あるサイトから `<form>` で POST される可能性は理論上ある。

現状の緩和策:

- SameSite Cookie（Supabase SSR 既定）
- 同一オリジンの fetch のみ UI から呼ぶ

改善案: `Origin` / `Referer` チェック、CSRF トークン → `07-未完了とFAQ.md`

## シナリオ E: 起動時 env 検証

### いつ動く？

`getSupabasePublicEnv()` が呼ばれるたび（client / server / middleware 初期化時）。

### service_role 混入検出

```6:19:lib/supabase/env.ts
function isServiceRoleKey(key: string): boolean {
  if (key.startsWith('sb_secret_')) return true;

  const payload = key.split('.')[1];
  if (!payload) return false;

  try {
    const normalized = payload.replace(/-/g, '+').replace(/_/g, '/');
    const padded = normalized.padEnd(Math.ceil(normalized.length / 4) * 4, '=');
    const decoded = JSON.parse(atob(padded)) as { role?: string };
    return decoded.role === 'service_role';
  } catch {
    return false;
  }
}
```

**JWT の構造:** `header.payload.signature`。payload を base64 decode して `role` を見る。

## まとめ: 読むときのチェックリスト

各操作を読むとき、次を自問する:

1. **認証:** 誰として操作している？（JWT / getUser）
2. **認可:** その操作をしてよい？（middleware / assert / RLS）
3. **入力:** データの形は正しい？（Zod / CHECK）
4. **表示:** 出力は安全？（React エスケープ / getSafeHttpUrl）
5. **運用:** 本番 Dashboard で何を設定する？（JWT expiry, rate limit）
