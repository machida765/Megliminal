⚡ トップページキャッシュ (ISR) の仕組み解説

Megliminal アプリにおける「トップページ高速化」と「DB負荷・通信量削減」の内部構造を図解した資料です。

1. どのような仕組みか（概要）

トップページ（/）は、ユーザーがアクセスするたびに Supabase データベースへSQLを発行して投稿を取得するのではなく、 サーバー（Next.js）が 5 分間（300秒）作り置きした HTML 画面を使い回して配信する仕組み（ISR: Incremental Static Regeneration） を採用しています。

💡 一言で言うと：
「誰がアクセスしても同じ『おすすめ＆新着投稿』の画面を、5分間に1回だけまとめて生成して全員に使い回す」仕組みです。

2. 修正前の問題点と今回の改善ポイント

項目 修正前（キャッシュが効かなかった原因） 改善後（現在の実装）
クライアント種別 cookies() を読むサーバークライアント（個人のログイン情報を参照） Public Client Cookie不使用の公開クライアント（lib/supabase/public.ts）
Next.jsの判定 「個人ごとに異なる動的ページ」と判定され、キャッシュが無効化されていた 静的スナップショット 「全ユーザー共通の固定ページ」と判定され ISR が有効化
DB問い合わせ（SQL） ユーザーがページを開くたびに毎回 SQL が発行されていた 5分に1回だけ サーバーが5分に1回だけ SQL を発行しHTMLを更新
カードコンポーネント PostCard が個別にカテゴリAPIを発行し連打が発生していた 親（トップ）からカテゴリ・小カテゴリを一括渡し＋メモリキャッシュ化で通信ゼロへ

3. アクセス時の具体的な処理の流れ

ケース A

初回アクセス または 5分経過後のアクセス (Cache MISS)

1. ユーザーがトップページにアクセス
2. サーバーが getPublicRepository().getHomePageData() で Supabase から最新の投稿・カテゴリを一括取得
3. サーバーが HTML 画面を組み立てて保存し、ユーザーに即座に返却（x-nextjs-cache: MISS）

ケース B

5分以内の2人目以降のアクセス (Cache HIT)

1. ユーザーがトップページにアクセス
2. Supabase への問い合わせ（SQL）は一切行わない
3. サーバーに保存されている作り置きの HTML を超高速（数ミリ秒）で返却（x-nextjs-cache: HIT）

4. 2層構造のキャッシュ最適化戦略

今回の改善では、サーバー側とブラウザ（クライアント）側の両面でキャッシュを最適化しています。

① サーバー側 (Next.js ISR)

export const revalidate = 300; // 300秒（5分）間 HTML を作り置き

トップページの構成要素（ヒーロー投稿・新着・人気・ランキング・統計・全カテゴリ）を一度のバッチ取得で一括生成します。

② ブラウザ（クライアント）側 (TanStack Query)

// hooks.ts staleTime: Infinity // カテゴリやタグなどのマスターデータはブラウザ上で永久キャッシュ

大カテゴリ・小カテゴリ・タグデータはアプリ起動中に一度取れば再取得しません。 また、投稿作成や削除を行った際は useInvalidate() により対象キャッシュのみを即座に自動最新化します。

5. この仕組みのメリットと注意点

メリット

  • 超高速な表示速度： DB問い合わせを挟まないため、ページが瞬時に開きます。
  • Supabase 転送量 (Egress) の節約： 無料枠上限（5GB）に達するリスクが激減します。
  • サーバー負荷軽減： 大量のアクセスがあっても DB サーバーがダウンしません。

注意点（仕様）

  • 新着投稿の反映が最大5分遅れる： 投稿直後はトップにすぐ反映されず、最大5分後の再生成タイミングで表示されます。（※検索画面 /search などはリアルタイムに取得されます）
